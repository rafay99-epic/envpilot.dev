On 2026-07-11 we merged two pull requests. [#101](https://github.com/rafay99-epic/envpilot.dev/pull/101) added CI/CD service tokens so a GitHub Action could pull secrets. [#103](https://github.com/rafay99-epic/envpilot.dev/pull/103) added the public REST API, an MCP server, and an API keys platform. Both landed the same day. Both created a table holding a SHA-256 hash of a bearer credential issued to a machine.

That is the whole problem. Same primitive, implemented twice, because the two features were designed in parallel by someone who did not stop to notice they were the same feature.

Here is what the two features looked like the week before the collapse:

<Mermaid name="one-token-model-before" />

Two tables. Two management surfaces (project settings versus org settings). Three tier flags: `cicd_service_tokens`, `public_api`, `mcp_server`. Two authorization code paths, one of which our own `CLAUDE.md` says must never exist — the invariant is "route EVERY request through `convex/features/api/authorize.ts::_authorizeRequest` — never re-implement authorization for a new surface."

The credential type lived seven days. It was born on 2026-07-11 in #101 and retired on 2026-07-18 in [#147](https://github.com/rafay99-epic/envpilot.dev/pull/147).

## The thing that made it urgent was not a breach

There was no incident. Nobody leaked a token. What made it urgent was that the duplication was still cheap to remove and was about to stop being cheap.

`apiKeys` already had the richer model: org-scoped, with `scopeProjects` (either `"all"` or a project list), `scopeEnvironments`, `scopeResources`, optional expiry. `serviceTokens` was strictly a subset — one project, a list of environments, read-only. The schema comment on `apiKeys` in `convex/schema.ts` had said so since the day it was written: it "Evolves serviceTokens into a scoped platform."

The `migrate-service-tokens` migration existed before any of this work, and its own description string was an admission that we were living with a fork:

> "NOT a one-time migration: serviceTokens still receives live inserts from the CI/CD tab, so re-run this whenever new tokens are created there. Retiring serviceTokens creation is a separate decision."

A migration you have to run forever is not a migration. It is a synchronization job between two systems of record, and it exists because nobody made the separate decision.

## The design: one nullable field, not a new abstraction

The obvious design — the one we rejected — was a `credentialType` discriminator on `apiKeys` with per-type validation branches. That reproduces the fork inside one table and buys nothing: you still have two shapes, two sets of rules, two mental models, just colocated.

What we shipped instead is one optional array:

```ts
surfaces: v.optional(
  v.array(
    v.union(
      v.literal("github_action"),
      v.literal("rest_api"),
      v.literal("mcp_server")
    )
  )
);
```

Optional is doing all the work. A key minted before the field exists has `surfaces === undefined` and stays valid on every surface — grandfathered into exactly the behavior it was minted under, which is the only backwards-compatible answer that is not a silent privilege change. Every key minted after is explicit.

That is also what made the migration safe. A `serviceTokens` row could become an `apiKeys` row without gaining power, because the drain stamped it (this migration shipped in #146 and was deleted in #147, once the drain was confirmed):

```ts
await ctx.db.insert("apiKeys", {
  organizationId: token.organizationId,
  name: token.name,
  tokenHash: token.tokenHash,
  scopeProjects: [token.projectId],
  scopeEnvironments: token.environments,
  scopeResources: ["variables"],
  // Service tokens were only ever an Action credential — stamp the
  // surface explicitly instead of grandfathering them onto all three.
  surfaces: ["github_action"],
  createdBy: token.createdBy,
  createdAt: token.createdAt,
  lastUsedAt: token.lastUsedAt,
  revokedAt: token.revokedAt,
  revokedBy: token.revokedBy,
});
```

Then the enforcement side, in `convex/features/api/authorize.ts`:

```ts
const surface =
  args.surface ??
  (args.gateFeature === "mcp_server" ? "mcp_server" : "rest_api");
if (key.surfaces !== undefined && !key.surfaces.includes(surface)) {
  await logDenied(key, "surface_out_of_scope");
  return { ok: false as const, denied: "surface_scope" as const };
}
```

The same file carries the honest caveat, in-code, because it is the kind of thing that gets forgotten and then over-claimed in a security page:

```ts
// KNOWN LIMIT: `surface` is caller-asserted, not transport-derived —
// the reads/requests actions are the shared backend of both HTTP
// surfaces, so a key holder calling Convex directly can claim either
// surface. The field segments well-behaved surfaces (a leaked Action
// key stays useless on REST/MCP routes); the hard security boundary
// remains the key's resource/environment/project scope + tier gates,
// which no claimed surface can widen.
```

The tier gate is derived from the surface rather than passed alongside it, so a caller cannot pair the MCP surface with the `public_api` gate to outlive its own gate being switched off:

```ts
const gate = await checkBooleanFeature(
  ctx.db,
  key.organizationId,
  args.surface !== undefined
    ? args.surface === "mcp_server"
      ? "mcp_server"
      : "public_api"
    : (args.gateFeature ?? "public_api")
);
```

And because a GitHub Action key is the one shape where the endpoint takes no project parameter, its shape is locked at mint time in `convex/features/api/keys.ts`:

```ts
if (surfaces.includes("github_action")) {
  if (scopeProjects === "all" || scopeProjects.length !== 1) {
    throw new ConvexError(
      "A GitHub Action key must be scoped to exactly one project — the Action's pull endpoint takes no project parameter, the key IS the project scope"
    );
  }
  if (scopeResources.length !== 1 || scopeResources[0] !== "variables") {
    throw new ConvexError(
      'A GitHub Action key must have exactly the "variables" resource — that is all the Action pulls, and an Action credential must not double as broader REST/MCP access'
    );
  }
}
```

## The bug that only existed because the migration predated the field

The drain migration was older than `surfaces`. Rows it had already copied in earlier runs landed with `surfaces === undefined` — which, by the grandfathering rule we had just written, means valid on all three surfaces. A CI token drained last week would have silently become a REST and MCP credential.

The fix was a backfill branch on the already-exists path, rerun-stable because the token hash is the identity:

```ts
if (existing) {
  // Rows copied by earlier runs predate the surfaces field and would
  // otherwise stay grandfathered onto EVERY surface — a leaked CI
  // token must never widen into a REST/MCP credential. Same tokenHash
  // = same credential, so stamping is always correct here.
  if (existing.surfaces === undefined) {
    await ctx.db.patch(existing._id, { surfaces: ["github_action"] });
    backfilled++;
  } else {
    skipped++;
  }
  continue;
}
```

This is the general shape of the trap: a backwards-compatibility default that is correct for the population it was designed for (keys a human minted through the wizard) and wrong for a population that arrives through a side door (rows a migration wrote). "Absent means permissive" is only safe if you enumerate every writer.

## Why it had to be two PRs

[#146](https://github.com/rafay99-epic/envpilot.dev/pull/146) shipped the model, the enforcement, the wizard changes, and stopped the CI/CD tab from minting new tokens — and deliberately left the `serviceTokens` table alive. Its body lists what it is not doing:

> serviceTokens table drop, pull-path fallback removal, `cicd/tokens.ts` deletion, `securityHold`/`SuspendMemberDialog` service_token removal, `cicd_service_tokens` registry retirement.

#147's body states the gate:

> **Merge only after the prod drain is confirmed** (run `migrate-service-tokens` from the admin panel post-#146 deploy until it reports 0 migrated; it also backfills surfaces on previously-migrated rows).

The split is not stylistic. A single PR cannot express "deploy this, then verify it against live production data, then delete the table." The verification step happens between two deploys, and there is no way to put a deploy boundary in the middle of a diff.

The reason the ordering matters is that the retirement is deliberately lossy in one direction. Before #147, `_authorizePull` checked `apiKeys` and fell back to `serviceTokens`. #147 deleted the fallback, and what stands at the end of that function today is:

```ts
// Unknown hash: nothing to attribute the attempt to — no audit
// possible. The serviceTokens fallback that used to live here is gone:
// the table was drained into apiKeys before its retirement.
return { ok: false as const, denied: "invalid_token" as const };
```

An undrained token does not degrade. It becomes an unknown hash and gets a flat `invalid_token`, with no audit record, because there is nothing left to attribute the attempt to. That is why "0 migrated" is a precondition and not a nice-to-have.

## What we built with the room it freed

Once there is one key model with a `resource` list, adding a capability is adding a string. `VALID_RESOURCES` became `["variables", "accounts", "projects", "requests"]` — and `requests` is the only mutating capability a key can hold.

It exists because of a specific failure mode. An agent using the MCP server hits a variable outside its scope, gets a `resource_scope` denial, and has nowhere to go. The human has to notice, go to the dashboard, and add it. So we let the machine file the request itself — and then constrained it hard.

<Mermaid name="one-token-model-machine-request" />

Three constraints carry the whole design.

**The request is valueless.** `vaultRef: undefined`. An agent never proposes a secret value; the human types it at approval time via `approveWithValue`. A `vaultRef` is never in anything returned to a machine caller.

**`github_action` keys can never carry `requests`.** CI cannot wait on human approval, so the shape validator rejects the combination outright.

**The machine path reuses `insertRequest`**, the same core the human dashboard path uses. That is what keeps the per-environment key-uniqueness invariant (`findEnvironmentConflicts`) enforced exactly once. A second write path is how that invariant would have quietly forked.

The one non-obvious piece is dedupe. Human requests dedupe per requester, because two developers can legitimately race the same key and the reviewer resolves it. Machine requests deliberately ignore who filed them:

```ts
// Machine dedupe ignores WHO filed it: an agent gains nothing from a
// second identical pending request, and per-requester dedupe would let
// key rotation bypass the guard. Humans keep per-requester dedupe (two
// developers may legitimately race the same key; the reviewer resolves).
const hasPendingDuplicate = pendingForKey.some(
  (request) =>
    request.status === "pending" &&
    (args.requestedByKeyId !== undefined ||
      request.requestedBy === args.requestedBy) &&
    // A pending request for DISJOINT environments is a different variable.
    request.environments.some((env) => args.environments.includes(env))
);
```

Per-requester dedupe would have been a guard you defeat by minting a new key.

Anti-spam is three chosen bounds, not measured ones: a `machineRequestCreate` token bucket at rate 5 per hour with capacity 2, a standing cap of `MAX_OPEN_MACHINE_REQUESTS_PER_KEY = 5`, and a 24-hour rejection cooldown that hands the reviewer's reason back so the agent learns why rather than retrying blind:

```ts
throw new ConvexError(
  `A request for "${args.key}" was rejected in the last 24 hours${
    recentRejection.reviewReason ? ` ("${recentRejection.reviewReason}")` : ""
  } — do not re-file it; ask the user to talk to their reviewer instead`
);
```

## What adversarial review caught

Both PRs went through a three-dimension adversarial review (correctness, security, simplicity) plus cubic, with the findings fixed in a second commit inside each squash. #146 reports 10 verified findings; #147 reports 16 across two passes. The ones worth naming:

- Environment names were not validated in the shared `insertRequest` core, so an unknown environment name from the machine create path produced a **permanently unapprovable request** — the reviewer's approve-time environment validation rejects the name the request was filed with; worse, it could have created a variable tagged with a nonexistent environment.
- `_readKeyRequests` used the `(requestedByKeyId, status)` index with an unbound status, which orders by status before recency, so old rejected rows could shadow a live pending one. Fixed by taking a bounded newest-first window per status and merging:

```ts
const perStatus = await Promise.all(
  REQUEST_STATUSES.map((status) =>
    ctx.db
      .query("environmentVariableRequests")
      .withIndex("by_requested_key_and_status", (q) =>
        q.eq("requestedByKeyId", args.keyId).eq("status", status)
      )
      .order("desc")
      .take(20)
  )
);
```

- `review` now authorizes org membership and reviewer capability **before** disclosing request status or origin-key liveness cross-org.
- `approveWithValue` preflights pending and valueless state before the Vault write, so a doomed call stops minting secret objects.
- The stale-request TTL sweep processes a bounded oldest-first batch, so a large pending backlog cannot blow the transaction and roll the whole thing back.
- From #146: `surface_scope` denials map to a 403 `FORBIDDEN_SURFACE` instead of a 500 and a stream of Sentry noise.

The one that is least like a bug and most like a design control is the MCP tool description for `envpilot_request_variable`. It is prompt engineering doing security work — the text is the only thing standing between a well-behaved agent and a retry loop:

> "File a request for an environment variable this key cannot read — a HUMAN reviewer must approve it in the Envpilot dashboard and supply the secret value; nothing is created until they do. [...] Never proposes secret values. Strictly rate limited — do NOT retry in a loop."

We do not rely on it. The rate limit is the actual enforcement. But an agent that reads the description does the right thing on the first try instead of burning its bucket.

## What this still does not solve

`convex/features/cicd/pull.ts` is still a second authorizer. The GitHub Action pull path does not route through `_authorizeRequest`; it has its own inline revoked/expired/surface/scope/gate ladder and re-derives the token hash rather than calling `hashToken` from `features/api/helpers.ts`. The invariant we wrote down has exactly one standing exception, and it is the oldest surface. That is the next thing to delete.

The surface field is caller-asserted, as the comment says. It segments well-behaved surfaces and it does not survive a key holder calling Convex directly. The real boundary is still scope plus tier gates.

The `cicd_service_tokens` rows survive in production feature-registry tables even though nothing reads them, and any leftover `serviceTokens` rows are now unvalidated data that Convex will keep until someone purges them from the dashboard. Per-key usage is a bounded audit scan rather than a counter, marked in `convex/features/api/keys.ts` with a `ponytail:` comment naming the upgrade path — day-bucket counter rows, if any org outgrows the window.

None of that is urgent. All of it is the cost of collapsing two things into one without stopping the world, which is the trade we would make again.
