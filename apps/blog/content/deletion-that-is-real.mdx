Envpilot stores secrets in two places at once. Convex holds the metadata — the `environmentVariables` row, its `variableVersions` history, its `variablePermissions` grants — plus an opaque string called `vaultRef`. WorkOS Vault holds the ciphertext that `vaultRef` points at. Every interesting bug we shipped in the first week of July 2026 lived at that seam, and they all had the same shape: the UI operated on the Convex side and made a claim about the Vault side that was not true.

Two claims in particular. "Rolled back to version 3." And "Deleted."

## The pointer that pointed at itself

Version history looked correct from the outside. Every write inserted a `variableVersions` row snapshotting the description, the environments, the version number, and the `vaultRef`. Rollback was a pointer flip: patch the variable's `vaultRef` to the target version's `vaultRef`, bump the version, log it.

The problem was on the write path. The web PATCH route called WorkOS Vault's in-place update:

```ts
let vaultRef: string | undefined;
if (value !== undefined) {
  const vaultResult = await updateSecret(variable.vaultRef, value);
  vaultRef = vaultResult.id;
}
```

`updateSecret` overwrites the object in place. Same object id, new contents. So every version row for a given variable stored the _same_ `vaultRef` — the live one. Rollback flipped a pointer to itself and reported success.

```text
BEFORE  (in-place update: every version row aims at one object)

  Convex                                   WorkOS Vault
  ┌────────────────────────────┐
  │ environmentVariables       │
  │   vaultRef ────────────────┼──────────┐
  ├────────────────────────────┤          ▼
  │ variableVersions           │       ┌────────────────┐
  │   v1 vaultRef ─────────────┼──────►│ obj_abc        │
  │   v2 vaultRef ─────────────┼──────►│ value = "v3"   │ ← overwritten
  │   v3 vaultRef ─────────────┼──────►│ (v1,v2 gone)   │   in place
  └────────────────────────────┘       └────────────────┘

  rollback(v1) = patch vaultRef := v1.vaultRef = obj_abc = current.
  UI says "restored". Nothing moved.
```

The obvious fix is to use the vendor's own versioning. WorkOS Vault does retain versions server-side, so before designing anything we probed the live API with a disposable object: create, update twice, list versions, then try to read an old one. Versions are retained. But no API surface returns a historical version's _value_ — reads by version id 404, version query params are ignored. Native versioning was legible and useless.

Which left one design, and it was already in our codebase. The CLI bulk-push route had always minted a fresh Vault object per write. [PR #78](https://github.com/rafay99-epic/envpilot.dev/pull/78) unified the web PATCH path onto that behavior. The diff is two words:

```diff
-      const vaultResult = await updateSecret(variable.vaultRef, value);
+      const vaultResult = await createSecret(variable.key, value, {
+        organizationId,
+        projectId: variable.projectId,
+      });
```

Now old refs stay referenced by earlier version rows as genuine immutable snapshots, and rollback remains a pointer flip — which means the server still never handles plaintext during a rollback. That property was worth keeping.

## The versions we could not fix

Every version row written _before_ #78 still shares one ref. Those values are gone from every reachable version, permanently. There is no backfill that can invent ciphertext that was overwritten.

So the question became what to tell the user. We picked disclosure over silence. The rollback mutation computes a single boolean and refuses to hide it:

```ts
// Versions created since value updates started minting a fresh vault
// object per change carry distinct vaultRefs, so this patch genuinely
// restores the secret value. Legacy versions (written while updates
// overwrote the vault object in place) share the variable's current
// vaultRef — for those, only metadata is restored.
const valueRestored = targetVersionRecord.vaultRef !== variable.vaultRef;
```

`valueRestored` goes into the `variable.rollback` audit log `details` and comes back in the mutation's return value. #78 shipped it to the API response and stopped there — because the app had no toast system at all. The one toast component in the tree was dead code, never rendered.

[PR #79](https://github.com/rafay99-epic/envpilot.dev/pull/79), merged 25 minutes later, added `sonner` and wired the disclosure:

```tsx
if (valueRestored) {
  toast.success(`Rolled back to version ${targetVersion}`, {
    description: "Value and settings restored.",
  });
} else {
  toast.warning(`Rolled back to version ${targetVersion} — settings only`, {
    description:
      "This version predates value history, so the secret value could not be restored and is unchanged.",
  });
}
```

While we were in there we solved the other half of the silence problem without auditing every call site. The Convex request manager routes every mutation and action failure through the client logger regardless of whether the caller catches the promise, so we hooked the logger instead:

```ts
error(...args: unknown[]) {
  const message = convexLogArgsToMessage(args);
  // Only mutation/action failures get a toast — the request manager tags
  // them "[CONVEX M(...)]" / "[CONVEX A(...)]".
  const isFunctionFailure = /\[CONVEX [MA]\(/.test(message);
```

One hook, deduped by message id. Query failures do not pass through here — they throw into React render and get caught by the `error.tsx` boundaries.

## Delete had never deleted anything

#78's body flagged its own debt: no delete path had ever removed a secret from WorkOS Vault, and minting a fresh object per value edit made that leak _worse_ by a factor of however many times you had edited the variable.

Deleting a variable set `deletedAt` and hid the row. The ciphertext stayed in Vault forever. And because there was no user-facing restore, the soft delete was not buying the user anything either — it was pure downside on both ends.

[PR #80](https://github.com/rafay99-epic/envpilot.dev/pull/80) landed 87 minutes after #78 and defined the model: delete is a 7-day trash window, then the row and every Vault object behind it are destroyed for real. The ordering is the entire design.

```text
  user clicks Delete
        │
        ▼
  patch { deletedAt: now }        rows hidden; Vault object UNTOUCHED
        │
        ├──── within 7 days ────► restore()
        │                          guard: past the window → REFUSE
        │                          (purge-eligible ⇒ un-restorable, so
        │                           GC can never race a restore)
        │
        │      OR "Empty trash" ──► emptyProjectTrash(), same ordering
        ▼
  cron 04:00 UTC → purgeExpiredBatch(depth)
        │
        ├─ WORKOS_API_KEY unset? ──► ABORT. 0 rows deleted.
        ▼
  listPurgeEligible()   by_deleted_at, gt(0)..lt(cutoff), take(25)
        │  refs = Set{ variable.vaultRef, ...versions[].vaultRef }
        ▼
  DELETE api.workos.com/vault/v1/kv/{ref}
        2xx | 404 | 410 → ok
        anything else   → skip THIS doc only, Sentry, retry next run
        │
        ▼  only if EVERY ref confirmed gone
  hardDeleteVariable()  re-check window, delete versions +
        │               permissions + doc.  auditLogs are KEPT.
        ▼
  full batch and depth+1 < 20 ──► scheduler.runAfter(0, depth+1)
```

Two details in there carry most of the safety.

The first is the direction of the failure bias. If `WORKOS_API_KEY` is missing from the Convex deployment environment, we abort having deleted nothing:

```ts
const apiKey = process.env.WORKOS_API_KEY;
if (!apiKey) {
  // Never destroy DB rows while the Vault copy survives.
  console.error(
    "[vaultGc] WORKOS_API_KEY is not set in the Convex environment — " +
      "aborting purge. No rows deleted (would orphan live Vault secrets)."
  );
  return {
    aborted: true,
    purgedVariables: 0,
    purgedAccounts: 0,
    skipped: 0,
    rescheduled: false,
  };
}
```

A leaked ciphertext is recoverable debt: the row still points at it, so a later run can find and destroy it. A DB row deleted while the ciphertext survives is an unreferenced secret nobody can ever find again. Given a choice, leak.

The second is that 404 and 410 count as success. That is what makes "retry on the next run" safe — a doc whose refs were half-deleted before a failure can finish next time without the already-gone refs blocking it forever.

And the `Set` around the refs exists purely because of the bug from #78. Legacy version rows share one ref, so a naive loop would issue N DELETEs for the same object. The old bug shaped the cleanup code that outlived it.

Audit logs survive the purge. `hardDeleteVariable` removes versions, permissions, and the doc — never `auditLogs`. The record that a secret existed and was destroyed outlives the secret.

### Two cascade bugs we only found by asking

Building trash forced the question "what happens to children when you delete a project?", and the answer was two real bugs. Version rows were _hard_-deleted immediately with no Vault cleanup, so restoring a project lost its history and leaked the ciphertext at the same time. Shared accounts were never touched at all — they stayed active under a deleted project. Both fixed in #80.

Our automated reviewer earned its keep here too. `getDeleted` was originally `by_project` + `take(500)` + an in-memory `deletedAt` filter, which silently hides the entire trash for any project with more than 500 active variables. We fixed it with a compound `by_project_deleted` index, and rejected the suggested fix of reusing the global `by_deleted_at` — that is a worse range scan.

## Moving the crypto behind the wall

[PR #86](https://github.com/rafay99-epic/envpilot.dev/pull/86) ("Stage 3") deleted `apps/web/src/lib/vault.ts`, `lib/vault-config.ts`, the `useVault` hook, and the `/api/vault/{keys,encrypt}` routes, and made `convex/vault.ts` the only home for `createSecret` / `readSecret` / `updateSecret` / `deleteSecret` as internal-only actions over the raw Vault REST API. Net −3504 lines against +2385.

The interesting part is the mistake. The PR notes the initial pass deleted `/api/vault` believing it was dead, but five live callers used it and dashboard reveals 404'd. The naive recovery — restore the route as it was — would have exposed `readSecret`, which has no authorization of its own. So the route came back as a thin session-authenticated wrapper that forwards the caller's JWT (same response shape, callers unchanged), and the authorization moved behind it into `canRevealVaultRef`: reverse-look-up the row that owns the ref via new `by_vaultRef` indexes on `environmentVariables`, `variableVersions`, and `projectAccounts`, then run the same per-resource check the rest of the app uses. Authorization by resource, not by a client-supplied org id. Unknown refs fail closed. And soft-deleted variables refuse to reveal even inside their restore window.

## Where orphans can still come from

The value-write actions are two-phase — Vault first, Convex second — so a failure between them orphans a secret. `createWithValue` has two guards:

```ts
// Reject environment clashes BEFORE writing the value to the vault — the
// create mutation re-checks (race-safe backstop), but failing only there
// left an orphaned vault secret behind for every clash.
// ...
const envClashes: string[] = await ctx.runQuery(/* ... */);
if (envClashes.length > 0) throw new ConvexError(/* ... */);

const vault = await ctx.runAction(internal.features.vault.vault.createSecret, {...});

try {
  variableId = await ctx.runMutation(api.features.variables.mutations.create, {...});
} catch (error) {
  // The DB row never materialized — don't leave the secret orphaned.
  await ctx
    .runAction(internal.features.vault.vault.deleteSecret, { vaultRef: vault.id })
    .catch(() => {});
  throw error;
}
```

A pre-check for the common failure, a compensating delete for everything else. `updateWithValue` carries the same pattern with the comment `// Best-effort — vaultGc reconciles any straggler.`

Reading the GC, that last sentence does not hold. `listPurgeEligible` gathers refs _from Convex rows_ — an object no row points at is by definition not enumerable that way. If the compensating delete fails, nothing we shipped will ever find that object. We have not written the reconciliation job that would, and there is no obvious cheap way to do it without a full Vault listing.

## What this still does not solve

Pre-#78 versions stay metadata-only forever. That is permanent, disclosed at the moment of use, and one-time.

Shared accounts still have no version history — there is no versions table for `projectAccounts`, so account credential updates are still in-place overwrites. You can see the asymmetry in the GC itself: variables get a deduplicated ref set, accounts get `vaultRefs: [account.vaultRef]`, a single-element array. Named as a follow-up in #78, still true.

Restoring a project does not auto-restore its children; they stay individually restorable from trash within their own windows. And `PURGE_BATCH_SIZE = 25` with `MAX_RESCHEDULE_DEPTH = 20` caps a run at roughly 500 docs per type before it waits for tomorrow. That is a deliberate ceiling on external calls, not a limit anyone has hit.

The orphan reconciliation gap above is the one that bothers us most, because the comment in the code currently claims a backstop that does not exist.
