Envpilot had exactly one idea of who you are: a human holding a WorkOS AuthKit session cookie. Every read path in the product assumed it. That is fine right up until something without a browser needs a secret — a CI job, a deploy script, an agent in someone's editor. Those had no way in at all, which meant the actual workflow for CI was: open the Envpilot dashboard, reveal each variable, paste it into GitHub repo settings, and now you have two sources of truth and one of them rotates and the other does not.

So the first thing we shipped was the narrow fix. And the narrow fix is where the interesting part starts, because it was correct and it still had to be thrown away eight hours later.

## The narrow fix, and the shape it baked in

[#101](https://github.com/rafay99-epic/envpilot.dev/pull/101) added a `serviceTokens` table. Read-only. Only the SHA-256 hash stored — the plaintext (`envpk_` + 160 bits of hex) is shown exactly once at creation and lives only in the dialog's React state. Scoped to one project and an explicit list of environments. Pro-gated on a `cicd_service_tokens` registry flag, checked at creation _and_ on every pull, so a downgraded org's tokens stop working rather than grandfathering access forever. One endpoint consumed it, `GET /api/v1/secrets`, listed in `unauthenticatedPaths` in `apps/web/src/proxy.ts` so the session middleware would keep its hands off. A GitHub Action consumed that.

```yaml
- uses: rafay99-epic/envpilot-action@v1
  with:
    token: ${{ secrets.ENVPILOT_TOKEN }}
    environment: production
```

There is no `project` input. Deliberately: the token carries its project, so a token cannot be repointed at a different one by editing a workflow file. And minting a token _is_ granting read access, which is why creating one requires `project:manage_permissions` — that is the "hand a production token to a DevOps engineer who has no Envpilot account" case, and it should cost the same permission as any other grant.

All of that was right. The problem was the schema sentence underneath it: **one project, variables only**. A REST API key needs to say "every project in this org, variables and shared accounts, expires in 90 days." An MCP connection needs the same. Neither of those sentences is expressible in a token whose scope is a single project ID and a string array of environments.

We could have added `serviceTokensV2`, or made `projectId` nullable and bolted a `resources` column on. We didn't, for a reason that had nothing to do with the schema: three surfaces were about to exist, and the failure mode we were actually afraid of was each one growing its own authorization code. Three copies of "is this key revoked" drift. One of them eventually forgets the expiry check.

The design doc for the replacement opens with the rule, and the rule is the whole post:

> One enforcement core, three faces. The REST API, the MCP server, and the existing GitHub Action all authenticate with the SAME key system and call the SAME Convex actions (auth → scope → gate → rate limit → bounded read → audit). New surfaces never re-implement authorization.

## The core

[#103](https://github.com/rafay99-epic/envpilot.dev/pull/103) replaced the table with `apiKeys`, whose scope is dynamic — `scopeProjects: "all" | Id[]`, `scopeEnvironments: "all" | string[]`, `scopeResources` drawn, at the time, from `["variables","accounts","projects"]`, optional `expiresAt` — and put every decision in one `internalMutation`, `convex/features/api/authorize.ts::_authorizeRequest`.

Two things about that function are load-bearing and neither is obvious.

**It is a mutation, not a query, and denials are returned rather than thrown.**

```ts
/**
 * Denials are RETURNED, not thrown: a throwing mutation rolls back its own
 * writes, which would erase the denial audit entry. Callers map `ok: false`
 * back onto whatever HTTP status / MCP error shape their surface uses.
 */
```

A denial has to be written to `auditLogs` — a revoked key still being presented by some pipeline is the single highest-signal event this system produces. But Convex mutations are transactional, so `throw` inside one discards the insert you just did. Returning the denial as data is the only way the audit row survives the refusal. Any transactional backend has this shape; it just bites harder when the transaction boundary is invisible in the function signature.

**The caller and the audit log learn different things.**

```ts
// Unknown hash: nothing to attribute the attempt to — no audit possible.
if (!key) {
  return { ok: false as const, denied: "invalid_key" as const };
}

if (key.revokedAt !== undefined) {
  await logDenied(key, "revoked_key_used");
  return { ok: false as const, denied: "invalid_key" as const };
}

// Expiry gets the SAME uniform "invalid" answer as revocation — an
// expired key is not a distinct signal from a revoked one to the caller.
if (key.expiresAt !== undefined && key.expiresAt <= now) {
  await logDenied(key, "expired_key_used");
  return { ok: false as const, denied: "invalid_key" as const };
}
```

Three distinct reasons, one uniform answer over the wire. The org's audit log gets `revoked_key_used` or `expired_key_used`; an unknown hash gets nothing at all, because there is no organization to attribute it to. The same asymmetry runs through scope: `throwForDenial` in `convex/features/api/helpers.ts` maps `project_scope` onto the string `"Project not found"` — the exact message an unknown slug produces — so a key cannot be used to enumerate which projects exist outside its scope.

The tier gate re-runs on every single request, and refuses to accept a mismatched pair:

```ts
const gate = await checkBooleanFeature(
  ctx.db,
  key.organizationId,
  args.surface !== undefined
    ? args.surface === "mcp_server"
      ? "mcp_server"
      : "public_api"
    : (args.gateFeature ?? "public_api")
);
```

`public_api` and `mcp_server` are separate flags in the feature registry so the two surfaces can be priced and toggled independently — and a caller cannot check the MCP surface against the REST gate to outlive its own gate being switched off.

```text
  Authorization: Bearer envpk_<40 hex>
        │
        ├─ assertKeyFormat        ── cheap reject before any hashing
        ├─ hashToken (SHA-256)    ── plaintext never stored, never logged
        ├─ consumeRateLimit(hash) ── caps brute-forcing INVALID keys too;
        │                            deliberately OUTSIDE the core
        ▼
  _authorizeRequest  (internalMutation — an ATOMIC WRITE, not a query)
        │
        ├─ no row      ─► invalid_key        (no audit: no org to attribute to)
        ├─ revoked     ─► audit ─► invalid_key
        ├─ expired     ─► audit ─► invalid_key
        ├─ bad surface ─► audit ─► surface_scope
        ├─ bad scope   ─► audit ─► resource|environment|project_scope
        ├─ gate off    ─► audit ─► tier_gate
        └─ ok          ─► lastUsedAt patch (only if ≥60s stale) + audit
        │
        │   NOTE: RETURNED, never thrown — a throw rolls back the mutation
        │      and takes the denial audit row with it
        ▼
  bounded read: .take(MAX_PULL_ROWS + 1)
        ├─ > 1000 rows        ─► throw ─► 422 OVERFLOW      (never partial)
        └─ vault decrypt fail ─► throw ─► 503 DECRYPT_FAILED (never a sentinel)
```

Rate limiting sits in the caller, not the core, because the buckets differ by cost: `apiMetadata` is 120/min, `cicdPull` (value pulls) is 30/min. Keying the limiter on the token hash means invalid keys burn budget too, so a hash-guessing loop rate-limits itself.

The read side has two rules that are really the same rule — never lie about completeness:

```ts
const rows = await ctx.db
  .query("environmentVariables")
  .withIndex("by_project_deleted", (q) =>
    q.eq("projectId", args.projectId).eq("deletedAt", undefined)
  )
  .take(MAX_PULL_ROWS + 1);

if (rows.length > MAX_PULL_ROWS) {
  throw new Error(
    `Project has more than ${MAX_PULL_ROWS} active variables — refusing a partial pull. Contact support to raise the limit.`
  );
}
```

The `+ 1` is the entire trick. Take one past the cap so overflow is _detectable_, then refuse loudly instead of handing back a silently truncated list that makes a deploy succeed with three secrets missing. Same policy for decryption: if the vault fails on one variable, the whole pull aborts with a message naming the key, and the error log carries `projectId` and `key` and never the value.

## The surface field, honestly labelled

Each key carries `surfaces` — which machine faces may present it. It is enforced in the core. It is also, in the code's own words, not a security boundary:

```ts
// KNOWN LIMIT: `surface` is caller-asserted, not transport-derived —
// the reads/requests actions are the shared backend of both HTTP
// surfaces, so a key holder calling Convex directly can claim either
// surface. The field segments well-behaved surfaces (a leaked Action
// key stays useless on REST/MCP routes); the hard security boundary
// remains the key's resource/environment/project scope + tier gates,
// which no claimed surface can widen.
```

That comment exists because the alternative — deriving the surface from the transport — would mean the Convex actions could no longer be shared, which is the thing the whole design is for. We took segmentation over a boundary and wrote down which one we got.

The MCP route makes the same bet more visibly. Its `verifyToken` is:

```ts
if (!bearerToken || !bearerToken.startsWith("envpk_")) return undefined;
```

That looks like a hole. It is the opposite: a shape check, deliberately cheap, because hash lookup, revocation, expiry, scope, tier gate, rate limit and audit all happen per-tool-call inside the Convex actions. If the MCP handler did any of its own authorization, it would be a fourth place that can drift.

## Where the thesis breaks

Grep every caller of `_authorizeRequest` today and you get `convex/features/api/reads.ts` and `convex/features/api/requests.ts`. That is REST and MCP. The GitHub Action path is not in the list.

`convex/features/cicd/pull.ts` still runs `_authorizePull`, its own function, with its own denial union (`invalid_token | environment_scope | tier_gate_public_api`) and its own copy of the revoked check, the expiry check, the surface check, the environment scope check, the tier gate and the audit insert. Same shape, line by line, different function.

```text
  REST client   ──► /api/v1/**  ──► api/reads.ts ────┐
                                                     ├──► _authorizeRequest
  MCP client    ──► /api/mcp    ──► api/reads.ts ────┘         (the core)

  GitHub Action ──► /api/v1/secrets ──► cicd/pull.ts
                                        _authorizePull  ✗ does NOT call it
                                        └── re-implements the same checks
```

The core's own docstring hedges exactly around this: "the REST API, the MCP server, and (indirectly, via a compat lookup) the legacy CI/CD pull endpoint." _Indirectly, via a compat lookup_ is carrying a lot of weight in that sentence.

This is not an accident so much as an ordering problem, and it generalizes: an enforcement core is trivially easy to hold for surfaces you build _after_ it exists. The hard case is the surface that shipped first. [#146](https://github.com/rafay99-epic/envpilot.dev/pull/146) and [#147](https://github.com/rafay99-epic/envpilot.dev/pull/147) a week later moved the Action onto `apiKeys` and deleted `serviceTokens` entirely — so the _table_ converged. The _function_ did not. `_authorizePull` now reads `apiKeys` rows using its own duplicated logic, which is arguably worse than before: the duplication is less visible because both paths now touch the same table. Small tells confirm it is a real fork, not a stylistic one — the core throttles the `lastUsedAt` patch to once per 60 seconds so parallel CI pulls sharing a key don't OCC-contend on the row; `_authorizePull` patches it unconditionally.

There is a second bit of residue in the core itself: `gateFeature` is still an accepted argument, marked deprecated, kept alive for the window where Convex deploys before the web app does. And keys minted before `surfaces` existed have no `surfaces` array at all, which is read as "valid everywhere" — grandfathered.

## The Action, and getting it out of a private repo

Two details in `packages/github-action/src/main.ts` are worth more than the rest of the file.

```ts
// CRITICAL ORDER: mask every value before anything that could export or
// log it, so it is redacted in logs even if a later workflow step echoes
// it. Skip empty values — core.setSecret("") would mask every subsequent
// log line for the rest of the job.
for (const variable of variables) {
  if (variable.value !== "") {
    core.setSecret(variable.value);
  }
}
```

Masking before export is the invariant. The `!== ""` guard is the footgun inside the safety feature: `core.setSecret("")` matches everywhere, so one empty variable would redact every remaining line of the workflow log.

```ts
writeFileSync(envFile, content, { mode: 0o600 });
// writeFileSync only applies `mode` when creating a new file; chmod
// explicitly so an existing file at this path also ends up 0600.
chmodSync(envFile, 0o600);
```

Distribution was its own problem. GitHub resolves `uses: owner/repo@v1` against a public repo containing `action.yml` and a committed `dist/` at that ref; it cannot pull a subdirectory out of a private monorepo. So there is a public mirror, and the publish job is paranoid about what crosses:

```bash
rm -rf dist action.yml README.md LICENSE
cp -R "$WORKSPACE/packages/github-action/dist" dist
cp "$WORKSPACE/packages/github-action/action.yml" action.yml
...
git tag "v${VERSION}" && git push origin "v${VERSION}"
git tag -f "$MAJOR" && git push -f origin "$MAJOR"
```

`rm -rf` before `cp` so nothing accretes; four paths only, never monorepo source. The exact version tag is created once and skipped if it exists; the floating `v1` is force-moved, which is the convention that makes `@v1` pinners get non-breaking updates. Publishing requires an `ACTION_PUBLISH_TOKEN` — a fine-grained PAT with Contents read/write on the mirror repo and nothing else — and the job fails loudly with instructions when it is missing. Ordering is strict: if `convex/` changed in the same merge, the backend deploys first. Never ship a client ahead of the contract it calls.

The bootstrap was manual, and the evidence is still sitting in the repo. `packages/github-action/scripts/publish-public.sh` still carries, at the end of its header block:

```bash
# DO NOT RUN THIS YET — the public repo (rafay99-epic/envpilot-action) does
# not exist yet. This script is here so the publish step is documented and
# ready once the repo is created.
```

The repo exists. `v1.0.0` was published by hand. The warning was never updated.

## What this still doesn't solve

`_authorizePull` is the honest answer: the tagline says three faces share one core and two of them do. Collapsing it is a small diff and has stayed un-done through five PRs, which is how these things go — nothing is broken, so nothing forces it. Beyond that: `surface` remains caller-asserted and is documented as segmentation rather than a boundary; pre-`surfaces` keys are still grandfathered everywhere; the deprecated `gateFeature` argument is still accepted; MCP responses are SSE-framed because that is the package default; and OAuth for MCP was deferred, so today the connection is a bearer key you paste into a client config.

The thing worth keeping from this is not the design. It is that a rule like "new surfaces never re-implement authorization" only ever applies forward. The surface that existed before the rule does not migrate itself, and a year of confident comments will happily sit on top of it.
