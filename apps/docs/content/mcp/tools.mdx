# Tools

A [signed-in](/mcp/setup) connection gets eight tools. Your role decides what each one can see: the same projects, environments, variables and documentation you can read in the dashboard. Every value-returning call is audited against you.

## Read tools

| Tool                     | What it does                                                                                         |
| ------------------------ | ---------------------------------------------------------------------------------------------------- |
| `envpilot_list_projects` | List the projects you can see                                                                        |
| `envpilot_get_variables` | Variables for a project + environment, with optional `keys` / `prefix` / `metadata_only`             |
| `envpilot_get_variable`  | One variable by exact key                                                                            |
| `envpilot_search`        | Search project names/slugs and variable **keys**, never values. Bounded to 20 projects / 100 matches |
| `envpilot_search_docs`   | Full-text search over **published** documentation: titles and page bodies. Never returns drafts      |
| `envpilot_get_doc`       | One **published** page: its outline, one section, or up to 60,000 characters at a time with a cursor |

## Draft tools

An agent can write documentation drafts. Every draft ends at a person:

| Tool                        | What it does                                                                    |
| --------------------------- | ------------------------------------------------------------------------------- |
| `envpilot_create_doc`       | Propose a documentation page. Always creates a **draft**; a person publishes it |
| `envpilot_update_doc_draft` | Replace, append to, or replace one section of a draft you wrote                 |

A draft page is invisible to your team, and to every other agent, until a person publishes it. In Claude both tools carry `destructiveHint`, so Claude asks before each one.

Shared accounts, secret files and variable requests were only ever available to API keys and were removed with them. Use the dashboard or the CLI for those.

## Documentation tools in detail

### Drafts are invisible

`envpilot_create_doc` always writes a draft. Nothing over MCP can
publish, and `envpilot_search_docs` / `envpilot_get_doc` return **published
pages only** — a draft is not merely hidden from search, it cannot be fetched
by id either. That gate is what stops a page one agent wrote from reaching
another agent's context before a person has read it.

### Page count is capped by plan

`envpilot_create_doc` fails once the project or the organization is at its
page limit — 10 per project and 25 per organization on Free, unlimited on Pro.
The caps are the same numbers the dashboard enforces, so an agent cannot use
the MCP surface to walk around them. See [Plans & Limits](/limits/plans).

### Long pages: write in parts, read in pages

A single tool call carries its whole payload, so a very long page is slow for
the agent to produce in one go. Create the page with its first part, then add
the rest with `envpilot_update_doc_draft` (`mode: "append"`), or rewrite one
part with `mode: "replace_section"` and a section id. Every edit re-checks the
**whole** resulting body, so splitting text across calls cannot slip a secret
or an injected instruction past the scanner. Published pages cannot be edited
over MCP.

`envpilot_get_doc` returns at most 60,000 characters per call. Pass
`view: "outline"` for the section list, `section` for one section, and the
`nextCursor` from a response as `cursor` to keep reading. Breaks fall on
paragraph boundaries and never inside a code block, unless a single line or
code block is itself longer than 60,000 characters; that one is split at the
limit.

### Retrying safely

`envpilot_create_doc` accepts `client_ref`, a string the caller picks. A
second call with the same `client_ref` returns the first page instead of
creating a duplicate, as long as you can still reach that project. Use it when a call timed out and you cannot tell
whether it landed.

### Pages name variables, never values

A page may reference `API_BASE_URL`; it never contains the value. Resolving it
is the reader's own `envpilot_get_variables` call under their own role, so
reading documentation can never become reading secrets.

### Content is scanned on write

Every proposed page is checked before it is stored. Credential shapes (PEM
blocks, provider key prefixes, connection strings with inline passwords) are
rejected outright, and text instructing an agent to call a tool is refused.
High-entropy strings that are normal in API documentation — sample JWTs, base64
payloads, commit SHAs — pass through untouched.

## Cost of each call

| Tool                                                | Bucket                        | Audited |
| --------------------------------------------------- | ----------------------------- | ------- |
| `list_projects`, `search`, `search_docs`, `get_doc` | 120/min metadata              | No      |
| `get_variables`, `get_variable`                     | 30/min value pulls            | Yes     |
| `create_doc`                                        | 30/hour per person, burst 10  | Yes     |
| `update_doc_draft`                                  | 120/hour per person, burst 40 | Yes     |

## Limits

- A project you cannot see behaves exactly as if it does not exist.
- `envpilot_search` never returns values, only names and keys.
- There is no tool that writes a variable, uploads a file, publishes a documentation page, or approves a request. There is no plan on which one appears.
- Documentation search is full-text: whole words, with only the last term prefix-matched. It is not a substring match and does not correct typos.
