System summary

Sentry gives grouped failures, event counts, release tags, and environment tags. The repository contains the extension's Convex subscription client, Git commit guard, web documentation routes, and secret-file UI needed to verify whether each signal maps to an owned defect.

Data flow

Sentry issue and event evidence is mapped to current source locations, then classified as owned defect, stale-build symptom, third-party noise, or insufficiently instrumented failure. Only owned defects become implementation work; every fix gets a focused test and release-level verification.

02 / executive summary

What needs attention

Problem

Two extension subscriptions surface Convex server errors as unhandled promise rejections. The Git guard assumes .git is a directory, which fails for worktrees. Recent docs errors named missing symbols, but current main already defines those symbols, indicating stale or development-build drift. Secret-file telemetry records a generic failure with filtered cause data.

Proposed solution

Add explicit subscription error handlers and a bounded reconnect path; resolve hooks through Git rather than filesystem assumptions; prove docs bundles with clean build and route E2E coverage; preserve secret values while logging safe operation, capability, size, and sanitized error context.

Key decisions

  • Do not label current Sentry data as production until production tagging and release coverage are verified.
  • Keep expected auth/offline failures out of alertable Issues, while preserving actionable diagnostics.
  • Use Git's authoritative hook path for normal repos, worktrees, and configured custom paths.

Complexity and dependencies

Medium, spanning extension, Convex-facing error handling, web E2E, and observability. Dependencies: existing Vitest/Playwright suites, running local services for developer-owned E2E, Sentry release/environment configuration, and a published extension build.

04 / implementation

Ordered execution plan

  1. Lock scope and baseline

    Export the current Sentry issue list with issue ID, environment, release, event count, user count, first/last seen, and transaction. Confirm whether production events are missing because instrumentation uses non-production environment names or because production is healthy.

    Files/tools: Sentry project envpilot; apps/web/src/lib/logger.ts; Sentry initialization files. Exit: every issue assigned to owned, stale, external, or unknown.

  2. Harden Convex subscription failures

    Extend the three onUpdate registrations in apps/vscode-extension/src/services/convex.ts with a shared onError handler. Add a typed error callback to RealTimeSyncService, avoid duplicate capture during reconnect, transition to disconnected/reconnecting, and preserve the existing bounded retry behavior.

    Dependency: define whether server query errors should recreate the client or only subscriptions. Preserve sign-out behavior; never retry indefinitely or treat a terminal auth failure as healthy.

  3. Fix Git hook path resolution

    Replace manual .git/hooks construction in apps/vscode-extension/src/services/gitCommitGuard.ts with Git's resolved hooks path. Handle empty output, non-repository folders, worktrees, bare-repo edge cases, and custom core.hooksPath. Keep existing hook content and marker update behavior unchanged.

    Regression cases: standard clone; linked worktree where .git is a file; relative and absolute custom hooks path; hooks path whose parent is a file; repository removed during activation.

  4. Prove docs release integrity

    Reproduce the docs routes from current main, run a clean web build, confirm DocStatusPill, Search, isSearching, and KindSwitch are present in the emitted release, and verify source-map release association. Add authenticated Playwright coverage for docs index, search, detail, shared resource kind switch, and direct refresh.

    Stop condition: if errors only reproduce on localhost/Turbopack or an old release, mark Sentry issues stale and fix release/environment tagging rather than changing working code.

  5. Make secret-file telemetry actionable

    Trace upload, replace, metadata update, and download separately through apps/web/src/app/(dashboard)/dashboard/projects/[slug]/files/page.tsx and the Convex file actions. Use stable event names and safe metadata: operation, file size, content type, environment count, browser/OS, error class, and sanitized Convex code. Never send file name, path, content, token, or secret value unless policy explicitly permits it.

    Regression cases: successful upload; quota denial; authorization denial; oversized payload; network interruption; retry after a failed upload; Windows path handling.

  6. Verify and close the loop

    Run focused extension unit tests and web checks, then the required developer-owned full Playwright suite. Publish a new extension/web release only after backend/client compatibility is confirmed. Re-query Sentry by release and environment for 24 hours, then resolve only issues whose new release has stopped reproducing.

    Repository rule: no dev server start from this agent. Use built-in checks; the developer performs final full-suite and release validation.

06 / acceptance

Testable completion conditions

  • Convex subscription failures call a controlled error path; no unhandled rejection is emitted for listMine or listForCaller.
  • Transient auth/network failure moves extension state to reconnecting/disconnected and recovers once; terminal sign-out does not create a retry storm.
  • Commit guard installs in standard repos and worktrees, respects Git-resolved custom hook paths, and preserves existing hooks.
  • Docs index, search, detail, sharing, and direct refresh pass against a clean production build; no missing-symbol runtime issues remain in the current release.
  • Secret-file events distinguish upload, replace, update, and download; Sentry payloads contain no secret material.
  • Release/environment tags let Sentry answer “what is failing in production?” without mixing local development and extension-host noise.
  • Focused checks pass; developer runs and records the full local Playwright suite before merge.
